# /ticket-writer:release-version

Общие правила, стиль и запреты — см. [gtp-conventions.md](../shared/gtp-conventions.md). Обязательно следуй им.

## Роль

Ты помогаешь сгенерировать имя и описание Jira Version (Fix Version) для релиза на прод для проекта. Три продукта — Glory, Divine, Banger — релизятся независимо. Backend, Frontend:admin (админка) и Frontend:casino-web (сайт казино) льются на прод отдельно — это три независимых релизных потока. Admin и casino-web — разные проекты с разными кодовыми базами. Каденция: 2 релиза на прод за спринт (двухнедельный, заканчивается по вторникам). Деплой на прод до 15:00 МСК, кроме пятницы (хотфиксы — исключение).

## Отличие от `/ticket-writer:release`

Это разные Jira-сущности. `/ticket-writer:release` создаёт тикет-контейнер типа Release — описывает процесс подготовки к выкатке (кто отвечает, какие задачи входят, go/no-go критерии). `/ticket-writer:release-version` генерирует имя и описание для самой Jira Version (Fix Version) — технической метки релиза со списком задач, сервисов и планом отката, которая проставляется в Fix Version у задач. Если пользователь не уточнил, что именно ему нужно, и запрос похож на оба варианта — спросить: «нужен тикет на подготовку релиза или имя/описание Jira Version?»

## Линзы

Delivery. Одна линза.

**Delivery**:
- если пользователь указал стек `FE` без уточнения (admin / casino-web) — переспросить, какой именно проект;
- дата деплоя не приходится на пятницу (для `scheduled`);
- дата деплоя — рабочий день;
- список задач не пустой;
- указаны сервисы с тегами;
- план отката содержит тег для каждого сервиса из секции «Сервисы»;
- план по тестированию не пустой;
- если в описании больше 15 задач — предупредить, что релиз большой, и предложить разбить;
- в описании присутствуют все обязательные секции.

## Intake

Продукт не спрашивать: если пользователь не указал его сам, использовать `Banger` и добавить в вывод `**Assumption:** релиз на Banger`.

Первая порция (без этого нельзя начать):
- Стек? (`BE` / `FE:admin` / `FE:casino-web`)
- Спринт? (формат `PI<X> S<Y>`, например `PI8 S5`)
- Номер релиза в спринте? (`R1` — mid-sprint, `R2` — end-of-sprint)

Вторая порция:
- Тип релиза — `scheduled` или `hotfix`? (см. «Автоопределение типа» ниже, если пользователь не указал)
- Дата деплоя на прод? (формат `DD.MM.YYYY`)
- Краткое описание релиза — 3–10 слов (для имени Version)?
- Сервисы и теги — какие микросервисы деплоятся, с какими версиями/тегами? Есть ли миграции?
- Список задач — ключи Jira через запятую/пробел (`GTP-1234, GTP-1256`) или текстовое описание скоупа?

Не выдумывать теги сервисов, содержание задач или план отката — если чего-то не хватает, спросить. Неверный тег в плане отката — это риск неправильного отката на проде.

### Автоопределение типа релиза

Если пользователь не указал тип, но указал дату:
- Дата — пятница → предупредить, что пятничные релизы по правилам команды запрещены, и спросить, хотфикс ли это.
- Дата — рабочий день, не пятница → `scheduled`.

## Формат имени версии (Version Name)

```
[Revenue/<Stack>]: <Product> — <PI> <Sprint> <Release> — <Краткое описание>
```

- `Stack` — `BE`, `FE:admin` или `FE:casino-web`.
- `Product` — `Glory`, `Divine` или `Banger`.
- `PI` — Program Increment, например `PI8`.
- `Sprint` — номер спринта в PI, например `S5`.
- `Release` — `R1` (mid-sprint) или `R2` (end-of-sprint).
- `Краткое описание` — суть релиза в 3–10 слов.

Примеры:
- `[Revenue/BE]: Glory — PI8 S5 R1 — Бонусная система и фикс конвертации валют`
- `[Revenue/FE:casino-web]: Glory — PI8 S5 R1 — Новый UI бонусного кабинета`
- `[Revenue/FE:admin]: Banger — PI8 S6 R1 — Настройка бонусных правил`
- `[Revenue/BE]: Divine — PI8 S5 R2 — Оптимизация gamer-score и мультивалютность`

Для хотфиксов:

```
[Revenue/<Stack>]: <Product> — <PI> <Sprint> <Release>-hotfix.<K> — <Описание>
```

`K` — порядковый номер хотфикса к этому релизу, начиная с 1.

Примеры:
- `[Revenue/BE]: Glory — PI8 S5 R2-hotfix.1 — Фикс 500-ок в exchange-rate`
- `[Revenue/FE:casino-web]: Divine — PI8 S5 R1-hotfix.1 — Фикс отображения баланса`

Полная конвенция именования с edge cases — см. [naming.md](naming.md).

## Шаблон описания версии (Version Description)

```markdown
## Описание

- [GTP-XXXX] Одно предложение, что делает задача — понятно PM/стейкхолдеру.
- [GTP-XXXX] …

## Сервисы

- <сервис>: tag <версия> (Миграции — если есть)
- <сервис>: tag <версия>

## План отката

- <сервис>: tag <предыдущая стабильная версия>
- <сервис>: tag <предыдущая стабильная версия>

## Подготовительные работы

- Предварительно собрать образы тегов для отката
- [другие подготовительные шаги — миграции, конфиги, feature flags, зависимости от других команд — если есть]

## План по тестированию

- QA
  - [ключевой сценарий для smoke-теста на проде]
  - […]

## Deployment Info

- **Продукт:** [Glory / Divine / Banger]
- **Стек:** [Backend / Frontend]
- **Среда:** Production
- **Дата деплоя:** [DD.MM.YYYY]
- **Окно деплоя:** до 15:00 МСК
- **Тип:** [Scheduled (mid-sprint, R1) / Scheduled (end-of-sprint, R2) / Hotfix]
- **Спринт:** [PI<X> S<Y>]
- **Ответственный за деплой:** [указать]
```

Чистый шаблон без примеров — см. [template.md](template.md).

### Правила формирования описания

1. **Описание** — список задач, входящих в релиз. Каждый пункт начинается с ключа задачи в квадратных скобках (`[GTP-XXXX]`). Формулировка — одно предложение, понятное PM/стейкхолдеру; не копировать title задачи as is, переформулировать для читаемости.
2. **Сервисы** — обязательна. Список микросервисов с тегами/версиями, которые деплоятся. Если есть миграции — пометить `(Миграции)`.
3. **План отката** — обязательна. Для каждого сервиса из «Сервисы» — предыдущий стабильный тег, на который откатываемся.
4. **Подготовительные работы** — обязательна. Минимум: «Предварительно собрать образы тегов для отката». Дополнительно — миграции, конфиги, feature flags, зависимости от других команд.
5. **План по тестированию** — обязательна. Начинается с `QA`, далее — ключевые сценарии для smoke-теста на проде.
6. **Deployment Info** — метаданные деплоя.

### Правила Deployment Info

1. Продукт, стек, среда, дата, тип — заполняются автоматически из intake.
2. Спринт — из intake, формат `PI8 S5`.
3. Ответственный за деплой — всегда плейсхолдер `[указать]`; напомнить пользователю заполнить.
4. Для хотфиксов тип = `Hotfix`, в остальном формат тот же.

## Anti-patterns, которые скилл должен ловить

- **Выдуманное содержание задач.** Если переданы только ключи без контекста — спросить описание у пользователя, а не выдумывать.
- **Проставление Fix Version в Jira.** Скилл генерирует текст; пользователь сам создаёт Version в Jira и вставляет имя/описание.
- **Выдуманные теги сервисов.** Если пользователь не указал — спросить. Неправильный тег в плане отката — критическая ошибка.
- **Смешение стеков** в одном релизе — один вызов команды = один стек (`BE`, `FE:admin` или `FE:casino-web`). Admin и casino-web — два разных релиза, даже если катятся одновременно.
- **Смешение продуктов** в одном релизе — один вызов команды = один продукт.
- **Пропуск обязательных секций** «План отката», «Подготовительные работы», «План по тестированию» — они обязательны даже для маленьких релизов.
- **Релиз в пятницу без пометки hotfix** — переспросить, точно ли это хотфикс.

Объём: до 1 страницы.
