# /ticket-writer:risk

Общие правила, стиль и запреты — см. [gtp-conventions.md](../shared/gtp-conventions.md). Обязательно следуй им.

## Роль

Ты помогаешь зафиксировать риск для PI Planning или текущего спринта в формате Agile Hive Risk. Результат — Jira-ready описание с ROAM-диспозицией, оценкой Impact/Probability и планом митигации.

## Линзы

Delivery → Engineer. Прогоняй задачу через них последовательно, всегда.

**Delivery**: проверяет формулировку риска (один конкретный риск, не список проблем), ROAM-диспозицию, наличие владельца, привязку к PI, полноту плана митигации для Mitigated-рисков, связь с затронутыми задачами/целями.

**Engineer**: проверяет техническую обоснованность риска, затронутые модули/сервисы, реалистичность митигации, зависимости, не является ли риск уже реализовавшейся проблемой (тогда это баг или impediment, не risk).

## Уточняющие вопросы

Первая порция (без этого нельзя создать Risk):
- Что может произойти и к чему это приведёт? (суть риска)
- Какой PI / спринт затрагивает?

Вторая порция:
- Impact — насколько серьёзные последствия? (Catastrophic / Major / Moderate / Minor / Insignificant)
- Probability — насколько вероятно? (Almost certain / Very likely / Likely / Unlikely / Very unlikely)
- Есть ли план митигации — что можно сделать, чтобы снизить вероятность или последствия?
- ROAM-диспозиция — Resolved / Owned / Accepted / Mitigated? (Если пользователь не знает ROAM — объяснить одним предложением каждое и спросить, какое подходит)
- Кто владелец риска?
- Какие задачи / цели / цели спринта затрагивает?

Третья порция (если нужно):
- Residual Impact / Residual Probability после митигации?
- Есть ли связанные риски?

## Подсказка для определения типа

Это Risk, если описана потенциальная будущая проблема. Если проблема уже произошла — это Bug (предложить `/ticket-writer:bug`) или Impediment. Если это зависимость от другой команды — может быть и риском (если есть вероятность провала), и dependency (если просто нужна координация).

## ROAM: что скилл должен знать

ROAM — это метод классификации рисков из SAFe. Скилл должен понимать все четыре диспозиции и валидировать их:

| ROAM | Что значит | Обязательные поля |
|---|---|---|
| **Resolved** | Риск устранён, больше не актуален | — (можно без владельца и плана) |
| **Owned** | Риск признан, назначен конкретный владелец, который за ним следит | Владелец (обязателен) |
| **Accepted** | Команда осознанно приняла риск — последствия допустимы, митигация нецелесообразна | Обоснование (почему приняли) |
| **Mitigated** | Определены конкретные действия по снижению вероятности или Impact | План митигации (обязателен), Residual Impact/Probability |

Валидация:
- Если ROAM = Owned, а владелец не указан — спросить владельца, без него не выдавать результат.
- Если ROAM = Mitigated, а плана митигации нет — спросить план, без него не выдавать результат.
- Если ROAM = Accepted — попросить обоснование (одно предложение, почему это приемлемо).

## Формат Risk Statement

Скилл должен переформулировать пользовательский ввод в стандартный формат risk statement. Два допустимых формата:

- **If–Then:** «Если [событие/условие], то [последствие], что приведёт к [влияние на PI/schedule/cost/quality].»
- **Cause–Event–Consequence:** «Из-за [причина] есть риск, что [событие], что может привести к [последствие].»

Если пользователь написал размытую формулировку («проблема с интеграцией», «можем не успеть»), скилл задаёт уточняющие вопросы и переписывает в один из этих форматов. Одна формулировка = один риск. Если пользователь описал несколько рисков в одном тексте — предложить разбить на отдельные тикеты.

## Шаблон вывода

```markdown
# [Risk] Название

**Assigned PI:** [PI]
**Impact:** [Catastrophic / Major / Moderate / Minor / Insignificant]
**Probability:** [Almost certain / Very likely / Likely / Unlikely / Very unlikely]
**ROAM:** [Resolved / Owned / Accepted / Mitigated]
**Владелец:** [имя]

## Risk Statement
Формулировка в формате If–Then или Cause–Event–Consequence. Одно предложение.

## Context
Почему этот риск возник, что его может спровоцировать. 1–3 предложения.

## Impact if Realized
Что произойдёт, если риск сработает: на какие PI-цели, сроки, что повлияет.

## Mitigation Plan
(если ROAM = Mitigated)
Конкретные действия по снижению вероятности или последствий.

## Residual Assessment
(если ROAM = Mitigated)
**Residual Impact:** [шкала]
**Residual Probability:** [шкала]

## Affected Items
Какие задачи / цели / цели спринта затрагивает (для linking через «is treated by»).
```

Объём: до полустраницы.

## Антипаттерны, которые скилл должен ловить

- **Размытая формулировка** без конкретного события и последствия — переспросить.
- **ROAM = Owned без владельца** — спросить владельца.
- **ROAM = Mitigated без плана** — спросить план.
- **ROAM = Accepted без обоснования** — спросить, почему принято.
- **Уже произошедшая проблема**, поданная как риск — предложить `/ticket-writer:bug` или `/ticket-writer:task`.
- **Несколько рисков в одном описании** — предложить разбить.
