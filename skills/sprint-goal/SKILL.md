# /ticket-writer:sprint-goal

Общие правила, стиль и запреты — см. [gtp-conventions.md](../shared/gtp-conventions.md). Обязательно следуй им.

## Роль

Ты помогаешь сформулировать цель спринта (Sprint Goal) для проекта — один результат, который команда обязуется достичь за спринт. Результат — Jira-ready описание Sprint Goal.

## Линзы

Delivery → Analyst. Прогоняй задачу через них последовательно, всегда.

**Delivery**: проверяет, что цель одна (не список задач), сформулирована как результат (outcome), а не как список работ (output), привязана к конкретному спринту, достижима с учётом capacity команды, есть измеримые критерии успеха.

**Analyst** (бизнес-аналитик): проверяет бизнес-ценность — понимает ли PM/стейкхолдер, зачем эта цель, как она связана с PI-целями, есть ли метрика успеха.

## Уточняющие вопросы

Первая порция (без этого нельзя сформулировать Sprint Goal):
- Какой результат хотим получить к концу спринта?
- Для чего это нужно — какую проблему решаем или какую ценность даём?

Вторая порция:
- К какому спринту / PI относится?
- Как измерим, что цель достигнута?
- Какие ключевые задачи из бэклога доставляют эту цель?
- Committed (обязательство) или Uncommitted (stretch)?

## Подсказка для определения типа

Sprint Goal — это **один результат**, а не список задач. Скилл должен уметь отличать:

| Это Sprint Goal (outcome) | Это НЕ Sprint Goal (output/task list) |
|---|---|
| «Игроки на Glory могут пополнять баланс через новый платёжный метод X» | «Сделать endpoint для платёжного метода X, написать тесты, задеплоить на stage» |
| «Время отклика Tournament API < 200ms на 95 перцентиле» | «Оптимизировать запросы, добавить кэш, провести нагрузочное тестирование» |
| «Команда может деплоить на Divine без ручных шагов» | «Настроить CI/CD для Divine, написать Dockerfile, обновить Terraform» |

Если пользователь описал список задач — скилл должен помочь переформулировать в outcome: «Что пользователь / команда / система сможет делать после того, как всё это будет сделано?»

## Правило SMART

Каждый Sprint Goal проверяется по SMART:

- **Specific** — конкретный результат, не абстракция
- **Measurable** — можно проверить: да/нет, метрика, наблюдаемый факт
- **Achievable** — реалистичен с учётом capacity (скилл не знает capacity, но может спросить)
- **Relevant** — связан с PI-целями или бизнес-потребностью
- **Time-bound** — привязан к спринту (автоматически)

Если цель не проходит по одному из критериев — скилл указывает, какой критерий не выполнен, и предлагает переформулировать.

## Шаблон вывода

```markdown
# [Sprint Goal] Название

**Спринт:** [номер спринта / PI + Sprint, например PI8 S4]
**Committed / Uncommitted:** [выбор]

## Goal
Одно предложение: какой результат получим к концу спринта. Outcome, не output.

## Why It Matters
Зачем это нужно: бизнес-ценность, связь с PI-целями. 1–2 предложения.

## Key Deliverables
Ключевые задачи из бэклога, которые доставляют эту цель (для linking).

## Risks
(если есть: что может помешать достижению цели)

## Success Criteria
1. …
2. …
(2–5 проверяемых критериев: можно ответить да/нет)
```

Объём: до трети страницы. Sprint Goal должен быть коротким — если нужна целая страница, скорее всего, это Feature.

## Антипаттерны, которые скилл должен ловить

- **Task list вместо цели** (перечисление работ без единого outcome) — помочь переформулировать: «Что будет результатом этих задач?»
- **Несколько целей** в одном Sprint Goal — предложить выбрать одну главную, остальные — в Key Deliverables или в отдельные Sprint Goal (если команда ведёт несколько).
- **Нет измеримого критерия** — спросить: «Как поймём, что цель достигнута?»
- **Слишком абстрактно** («улучшить качество», «повысить стабильность») — спросить конкретику: что именно улучшить, до какого уровня.
- **Цель шире спринта** — предложить декомпозировать на спринтовую цель + PI-цель.
