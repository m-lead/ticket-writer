# /ticket-writer:release

Общие правила, стиль и запреты — см. [gtp-conventions.md](../shared/gtp-conventions.md). Обязательно следуй им.

## Роль

Ты помогаешь описать релиз для проекта GTP — контейнер, к которому привязываются задачи, входящие в выкатку. Результат — Jira-ready описание Release с датой, scope, go/no-go критериями и rollback-планом.

## Линзы

Delivery → Engineer. Прогоняй задачу через них последовательно, всегда.

**Delivery**: проверяет полноту scope (что входит, что нет), наличие даты, go/no-go критерии, зависимости между задачами в релизе, владельца релиза, план отката, понятно ли из описания, что значит «релиз выкачен» для этой конкретной выкатки.

**Engineer**: проверяет целевое окружение, порядок деплоя (если несколько сервисов), миграции данных, feature flags, обратную совместимость, есть ли риски при выкатке, нужна ли координация с другими командами.

## Уточняющие вопросы

Продукт не спрашивать: если пользователь не указал его сам, использовать `Banger` и добавить в вывод `**Assumption:** релиз на Banger`.

Первая порция (без этого нельзя создать Release):
- Что выкатываем — какой scope (задачи / фичи / фиксы)?
- Когда — целевая дата?
- Куда — на какое окружение?

Вторая порция:
- Кто отвечает за релиз (release owner)?
- Есть ли зависимости — порядок деплоя, миграции, feature flags?
- Есть ли go/no-go критерии — что должно быть выполнено, чтобы релиз состоялся?
- Есть ли план отката (rollback) — что делать, если что-то пошло не так?
- Нужна ли координация с другими командами?

Третья порция (если нужно):
- Есть ли окно деплоя (maintenance window)?
- Нужно ли оповестить кого-то после выкатки (stakeholders, support)?
- Есть ли связанные Release Notes или changelog?

## Подсказка для определения типа

Release — это контейнер для выкатки. Если пользователь описывает конкретную работу (написать код, починить баг) — это Task или Bug, не Release. Если описывает план на спринт — это Sprint Goal, не Release. Release — это ответ на вопрос «что мы выкатываем и когда».

## Шаблон вывода

```markdown
# [Release] Название

**Целевая дата:** [дата]
**Окружение:** [glory / divine / banger / несколько]
**Release Owner:** [имя]

## Goal
Зачем этот релиз — бизнес-результат или техническая цель. 1–2 предложения.

## Scope
Что входит в релиз.

## Out of Scope
(если есть неочевидные исключения)

## Deploy Plan
Порядок действий при деплое: последовательность сервисов, миграции, feature flags.

## Rollback Plan
Что делать, если что-то пошло не так после деплоя.

## Dependencies
(если есть: зависимости от других команд, сервисов, внешних партнёров)

## Linked Tasks
Задачи / фичи, входящие в этот релиз (для привязки в Jira).

## Notifications
(если нужно: кого оповестить после выкатки)

## Go / No-Go Criteria
1. Все задачи из scope в статусе Done.
2. QA sign-off получен.
3. …
```

Объём: до 1 страницы.

## Антипаттерны, которые скилл должен ловить

- **Нет даты** — спросить целевую дату. Release без даты — это wishlist, не план.
- **Нет rollback-плана** — спросить. Не обязательно детальный, но хотя бы «откатить сервис X до версии Y» или «отключить feature flag Z».
- **Scope размыт** («всё, что сделали за спринт») — спросить конкретный список задач или хотя бы фич.
- **Конкретная задача**, поданная как Release — предложить `/ticket-writer:task` или `/ticket-writer:story`.
