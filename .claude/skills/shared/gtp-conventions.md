# GTP conventions

Общие правила для всех команд `/feature`, `/story`, `/task`, `/subtask`, `/bug`, `/research`, `/spike`, `/risk`, `/release`, `/sprint-goal`, `/retro-action`. Каждый SKILL.md ссылается сюда вместо дублирования.

## Контекст команды

- Команда Revenue Team, три продукта: Glory, Divine, Banger.
- Jira-проект **GTP**. Иерархия: Epic → Story / Task (один уровень) → Sub-task. Bug — отдельный тип.
- PI = 6 спринтов × 2 недели. 1 рабочий день = 6 продуктивных часов.
- Scope-решения принимает PM (Александр Голубин).
- Окружения: dev, purgatory (stage), stage, prod glory, prod divine, prod banger.
- ROAM-шкала для рисков: Resolved / Owned / Accepted / Mitigated.
- Impact-шкала: Catastrophic / Major / Moderate / Minor / Insignificant.
- Probability-шкала: Almost certain / Very likely / Likely / Unlikely / Very unlikely.

## Стиль

Пиши так, как написал бы толковый тимлид в Slack: коротко, по делу, без воды. Каждое предложение должно нести информацию — если его убрать и смысл не потеряется, значит оно лишнее.

### Чего не делать

**Канцеляризм.** Вот конкретные формулировки, которые не должно быть в описании задачи:

| Плохо (канцеляризм) | Хорошо (по-человечески) |
|---|---|
| В рамках данной задачи предполагается… | Нужно сделать… |
| Необходимо обеспечить корректную работу… | [название] должен работать так: … |
| С целью повышения качества… | Чтобы [конкретный результат]… |
| Данная функциональность предназначена для… | Это нужно для… / Это позволит… |
| Требуется реализовать механизм… | Добавить… |
| Следует произвести рефакторинг… | Отрефакторить… |
| Осуществить миграцию… | Мигрировать… / Перенести… |
| Произвести тестирование… | Протестировать… |
| Обеспечить возможность… | Дать возможность… / Сделать так, чтобы… |
| В соответствии с требованиями… | По требованиям… / Как договорились… |
| На основании полученных результатов… | По результатам… |
| Вышеуказанный / нижеуказанный | (просто назвать то, о чём речь) |

**Вода.** Слова и фразы, которые не несут информации:

| Пример воды | Почему это вода |
|---|---|
| «Это важная задача, которая…» | Все задачи в спринте важные, иначе их бы не брали |
| «Как всем известно…» | Если известно — не надо писать |
| «На сегодняшний день…» | Это когда? Указать конкретную дату или убрать |
| «В целом» / «в общем и целом» | Либо конкретизировать, либо убрать |
| «Так сказать» / «по сути» | Убрать |
| «Достаточно серьёзная проблема» | Какая именно? Указать влияние: «теряем X% конверсии» |
| «Различные улучшения» | Какие? Перечислить |

**Повторения.** Одна мысль — один раз. Если в Context написано «призовой фонд отображается некорректно», не нужно повторять это в Goal, Scope и AC разными словами. Context объясняет проблему, Goal — что хотим, Scope — границы, AC — как проверить. Каждая секция добавляет новую информацию, а не пересказывает предыдущую.

**Паттерны AI-речи.** Конкретные конструкции, которые выдают текст, написанный языковой моделью, и которые нужно избегать:

| Паттерн AI | Почему плохо | Как написать вместо |
|---|---|---|
| «Давайте рассмотрим…» | Мы не на лекции, мы пишем задачу | (просто начать описывать) |
| «Важно отметить, что…» | Если важно — просто напиши, без вступления | (написать факт) |
| «Стоит учесть следующие аспекты:» | Канцеляризм + AI-маркер | (перечислить что учесть) |
| «Данный подход позволяет…» | «Данный» — канцелярское слово, «подход» — абстракция | «Это позволяет…» или «Так мы получим…» |
| «Для достижения этой цели…» | Вводная конструкция без информации | (убрать, сразу написать что делать) |
| «Таким образом, мы можем…» | AI-маркер + лишнее слово | (убрать или заменить: «В итоге…») |
| «Резюмируя вышесказанное…» | Если нужно резюмировать — задача слишком длинная | (сократить задачу) |
| «Это обеспечит / гарантирует…» | Ничто не гарантирует; лучше сказать конкретно | «После этого X будет работать Y» |
| Перечисления с «во-первых, во-вторых, в-третьих» | AI-маркер; в задачах используй чеклисты | (чеклист: `- [ ] ...`) |
| «Ключевой момент / ключевая особенность» | Информационный шум | (убрать, написать факт) |

**Тест на качество текста.** Перед выдачей результата мысленно проверить: «Мог бы это написать живой тимлид в Slack за 5 минут?» Если текст звучит как выдержка из ТЗ, диплома или корпоративной презентации — переписать.

## Язык

Текст описания задачи — на русском.
Заголовки секций — на английском и русском:
- Английские: Context, Goal, Scope, Out of Scope, Acceptance Criteria, Dependencies / Blockers, Current Behavior → Expected Behavior, Suggested Task Breakdown, Questions to Answer, Technical Notes, QA Notes, Edge Cases, User Scenarios, User Story.
- Русские: Предусловия, Шаги воспроизведения, Фактический результат, Ожидаемый результат, Доказательства, Вопрос, Формат результата.

Технические термины — по принципу «как привычнее команде»:
- Простые и общепринятые — на английском, без перевода: API, endpoint, frontend, backend, deploy, release, service, DTO, migration, integration test, pull request, code review, sprint, story points, CI/CD, staging, production, bug, feature, scope, flow, MVP, hotfix, rollback, fallback, WIP, ETA, SLA.
- Составные или специфичные — на русском, с английским в скобках при первом упоминании: обратная совместимость (backward compatibility), нагрузочное тестирование (load testing), граничные случаи (edge cases), точка входа (entry point), бизнес-логика (business logic), критерии приёмки (acceptance criteria — но в заголовке пишем AC), пользовательский сценарий (user scenario), частота воспроизведения (reproduction rate), предусловия (preconditions), промежуточное окружение (staging environment).
- Названия сервисов, модулей, переменных, полей — всегда как в коде, без перевода: `exchange-rate`, `gamer-score`, `GTP`, `purgatory`.

Если есть сомнение — писать на русском с английским в скобках. Лучше разжевать один раз, чем потерять кого-то из команды, кто не знает термин.

## Продукт

Если пользователь указал продукт — вставить в описание. Если не указал — не додумывать и не спрашивать (если это не критично для AC).

## Общие правила: чего не выдумывать

Это критическая секция. Языковая модель склонна генерировать правдоподобные, но неверные детали — особенно в предметных областях, где много специфики. iGaming — именно такая область: платёжные провайдеры, compliance-требования, курсы валют, бонусные механики, регуляторные ограничения по юрисдикциям. Правдоподобная, но неверная деталь в описании задачи — это заложенная бомба: разработчик может начать реализацию, опираясь на выдуманное бизнес-правило.

### Категории запретов

**Бизнес-правила и бизнес-логика.** Не придумывать:
- правила начисления бонусов, cashback, loyalty points;
- условия акций и промо;
- лимиты ставок, депозитов, выводов;
- правила верификации (KYC/AML);
- формулы расчёта (GGR, NGR, комиссии);
- правила работы турниров, джекпотов;
- поведение системы при конкретных суммах или порогах.

Если нужно упомянуть бизнес-правило — сослаться на источник (Confluence, PM, Product Owner) или пометить `**TODO:** уточнить правило начисления бонуса у PM`.

**API и интеграции.** Не придумывать:
- названия endpoint-ов, полей, параметров;
- контракты между сервисами (request/response);
- названия и возможности платёжных провайдеров;
- форматы данных, которые приходят от внешних систем;
- поведение внешних API при ошибках.

Если нужно описать интеграцию — описать ожидаемое поведение на уровне «что должно происходить», а не «какой endpoint вызвать с какими параметрами». Конкретика — `**TODO:** уточнить контракт с [имя разработчика / название команды]`.

**Платёжные flow и compliance.** Особая зона риска. Не придумывать:
- последовательность шагов в платёжном flow (deposit, withdrawal, chargeback);
- требования регуляторов по конкретным юрисдикциям;
- правила работы конкретных платёжных методов (Visa, crypto, e-wallets);
- ставки конверсии и правила округления;
- требования к хранению персональных данных.

Любое предположение в этой области — `**TODO:** уточнить с командой Payments / compliance / PM`.

**Архитектурные решения.** Не придумывать:
- какой сервис за что отвечает (если не знаешь точно);
- как данные передаются между сервисами;
- какие базы данных используются;
- какие очереди, кэши, брокеры задействованы;
- решения о выборе технологий и паттернов.

Можно указать предполагаемый модуль/сервис и подписать `**Assumption:** задача относится к сервису X`. Разработчик поправит, если не так.

**Договорённости между командами.** Не придумывать:
- кто за что отвечает между командами;
- какие SLA между сервисами;
- какие есть договорённости по приоритетам, очерёдности, зонам ответственности.

Если задача затрагивает другую команду — `**TODO:** уточнить зону ответственности с [название команды]`.

**Сроки и оценки.** Не придумывать:
- сроки выполнения задачи;
- story points (если пользователь не указал);
- приоритет (если пользователь не указал);
- sprint (если пользователь не указал).

## Как оформлять незнание

Два маркера:

`**TODO:**` — когда информации нет и её нужно получить. Указать, у кого или где уточнить.
- `**TODO:** уточнить у Александра Голубина, входит ли Banger в scope`
- `**TODO:** проверить контракт endpoint /api/tournament/prize-pool`
- `**TODO:** уточнить у QA тест-кейсы для конвертации валют`

`**Assumption:**` — когда можно сделать разумное предположение, но оно требует подтверждения.
- `**Assumption:** проблема только на frontend, backend отдаёт корректные данные`
- `**Assumption:** поведение одинаковое для Glory и Divine`
- `**Assumption:** баг появился после последнего релиза`

Разница: TODO = «мы не знаем, нужно узнать». Assumption = «мы предполагаем вот это, но можем ошибаться». Оба маркера — это нормально. Задача с тремя TODO лучше, чем задача с тремя выдуманными фактами.

## AC

Каждый критерий — проверяемый (можно ответить да/нет). Формат: чеклист. Оптимально 3–8 критериев. Больше 8 — повод разбить задачу.

## Scope

Scope-решения принимает PM. Скилл может предложить сузить или разбить — но не решает за PM.

## Уточняющие вопросы

Задавать столько, сколько нужно для полной и ясной задачи. Не ограничивать себя.

Принципы:
- Задавать вопросы порциями: сначала самые важные (без которых нельзя определить тип или написать AC), потом уточняющие.
- Не задавать вопросы, ответ на которые уже есть в тексте пользователя.
- Если можно сделать разумное предположение — сделать и подписать `**Assumption:**`. Пользователь поправит, если не так.
- Формулировать вопросы конкретно: не «расскажите подробнее», а «на каком окружении воспроизводится?»
